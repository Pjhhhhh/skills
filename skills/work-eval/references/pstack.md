# pstack 验证与改进方法

pstack 的项目验证、性能测量、变更影响与反复错误约束方法用于补齐执行和验收中的实际缺口。按下列条件选择已安装且正文可读取的技能，沿用项目已有计划、验证入口和证据。技能的自动选择方式以当前宿主的有效元数据为准；缺少技能时继续可做的工作，必要项保留具体缺口与恢复条件。

## 业务验收

实现与自检完成后，先按原始用户目标、有效纠正和本轮实际影响核对 spec、ticket 与 Feature Map 的范围，再结合已知反例确定本次必要结果，沿用原记录关联前提、用户动作、可观察终态、副作用与证据。样式参考或能力目录中的既有业务按当前任务所需选用，关联回归按具体受影响行为选择；同仓库或目录列出本身不构成本轮完成门槛。已有代码、路由和 Feature Map 用于定位操作方式；要求中的必要功能尚无入口时，保留为未完成项。

按用户实际采用的默认入口与模式运行完整必要流程，观察操作过程、终态和相关副作用，优先复用项目验证技能及仍有效的证据。正常初入、历史回访、带参深链及准备好的数据条件分别支持各自结论；当前任务需要哪些路径就分别核验，技术参数在已确认的产品流程内处理。辅助入口通过的结果只支持其实际覆盖范围。简单任务的终态可由一次真实检查直接核验时，完成该检查即可。

验证入口自证可用后，继续对照原要求核对任务覆盖；Feature Map 的全量巡检覆盖已有映射，仍须补齐规格、票据和有效纠正中的漏项。发现工具无法观察必要结果时补充验证入口；产品结果不符合要求时回到原任务修复产品，再重跑原失败和受影响路径。无法完成的必要项保留具体原因与恢复条件。

## 驱动应用与维护验证入口

- **已有 `verify-<app>`**：按其中的 Launch／Doctor／Drive／Evidence／Cleanup 驱动应用，核对真实用户路径及副作用，保存操作和结果证据。
- **没有可靠项目验证入口，且需反复运行同一应用或用户明确要求生成**：使用 `create-verification-skill`，优先复用已有交互工具。生成的技能记录用户入口、前置条件、可重复命令、可观察终态和证据位置，并建立 Feature Map。交付前按生成的说明实际完成启动、检查、一个映射功能的操作及清理，确认清理后证据仍在；该次实跑证明新入口可用，整项任务仍按上述业务验收核对全部必要结果。
- **已有验证技能或 Feature Map 随应用变化而失效，或用户要求维护**：使用 `maintain-verification-skill`，覆盖全部映射功能的源码和真实交互，报告 clean／changed／blocked。已有验证技能无论由谁创建，均可按此维护；部分巡检写明已覆盖范围和剩余功能。该分支只修改验证技能自身目录，区分文档漂移、驱动工具缺口与产品错误，产品错误记录并交回原任务。

操作应用实例、端口、数据和清理产物前，核对相应授权。共享实例按顺序操作；首次运行或维护中出现失败时，保存失败证据，核对健康状态，修复可推进部分并重新驱动受影响功能。清理本次启动的实例与临时状态，按项目约定保留正式证据；具体归属和删除边界沿用当前有效规则。

## 性能测量

要给出性能数字或据此选型时，使用 `benchmark-checklist`，核对限制吞吐量的因素、各选项的比较条件、理论上限计算、错误数量与输出正确性、可复现性、端到端耗时占比，以及测量期间是否实际执行了目标工作。

用户明确只要求快速粗估时，可以只运行一次，仍须统计错误并检查输出正确性，确认目标工作确在计时区间内执行，并声明仅运行一次；该次结果异常时补做其余检查。比较多个选项时完成全部检查。

## 变更影响与反复错误

- **变更安全需要核对局部 diff 以外的影响**：使用 `blast-radius`，调查实际依赖、数据与时序，运行真实代码证明关键安全事实。交付已确认风险、已检查排除的风险、未证明项及可重跑证据，供原有代码审查或独立验收使用。
- **同一类已证实错误在本仓库反复出现**：使用 `correct`，先调查真实历史错误，再依次考虑架构、类型、lint／CI 和行为测试约束，最后编写文档与规则。每条新检查用真实历史错误证明能够检出该错误。
